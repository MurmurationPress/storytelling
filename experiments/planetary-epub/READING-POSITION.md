# Reading position, read-aloud and the publication boundary

Investigation: 2026-10-20, PR #1. **The typing component works. Reliable encounter triggering remains an integration problem.** This source investigation finds no supported publication-facing silent-reading enter/leave signal in official Thorium 3.5.1. Read-aloud uses location information that the reader already has; it does not make that information a public EPUB API.

No new research EPUB was built: none of the traced mechanisms supplies a credible new supported trigger. No new native test was performed in this step. Existing timed native evidence remains in [arrival-v1](evidence/arrival-v1/README.md), including the failed invisible-preload hypothesis. Playback-v2 and all existing EPUB bytes remain unchanged. This is a source/API finding, not new native verification or proof that all visibility heuristics are impossible.

## Native turn → reader location

1. [navLeftOrRight / navPreviousOrNext](https://github.com/edrlab/thorium-reader/blob/137e8901196bc47173580856105fe78b40473570/src/r2-xxx-js/r2-navigator-js/electron/renderer/location.ts#L464-L605) map native direction, RTL/spread and spine state. An in-document turn sends `R2_EVENT_PAGE_TURN` to the active webview; a spine turn selects a linked document.
2. [onEventPageTurn](https://github.com/edrlab/thorium-reader/blob/137e8901196bc47173580856105fe78b40473570/src/r2-xxx-js/r2-navigator-js/electron/renderer/webview/preload.ts#L947-L1267) changes reflowable column/scroll offsets. For fixed layout, or at a boundary, it returns `R2_EVENT_PAGE_TURN_RES`; the [host handler](https://github.com/edrlab/thorium-reader/blob/137e8901196bc47173580856105fe78b40473570/src/r2-xxx-js/r2-navigator-js/electron/renderer/location.ts#L273-L335) navigates to the adjacent spine item. A document load is only part of this process.
3. [onScrollRaw](https://github.com/edrlab/thorium-reader/blob/137e8901196bc47173580856105fe78b40473570/src/r2-xxx-js/r2-navigator-js/electron/renderer/webview/preload.ts#L2435-L2512) and [processXY / visible-element selection](https://github.com/edrlab/thorium-reader/blob/137e8901196bc47173580856105fe78b40473570/src/r2-xxx-js/r2-navigator-js/electron/renderer/webview/preload.ts#L3975-L4240) establish a viewport anchor, stored as `locationHashOverride`. Location notifications are debounced; an anchor is not a complete list of all presented components.
4. [notifyReadingLocationRaw](https://github.com/edrlab/thorium-reader/blob/137e8901196bc47173580856105fe78b40473570/src/r2-xxx-js/r2-navigator-js/electron/renderer/webview/preload.ts#L5092-L5315) builds selector, caret/range, progression, pagination, selection and text data, then **sends to the host** via Electron `ipcRenderer.sendToHost(R2_EVENT_READING_LOCATION, ...)`.
5. [_saveReadingLocation / setReadingLocationSaver](https://github.com/edrlab/thorium-reader/blob/137e8901196bc47173580856105fe78b40473570/src/r2-xxx-js/r2-navigator-js/electron/renderer/location.ts#L1834-L1952) associates the active document href and stores a `LocatorExtended`, invoking the application's callback. Thorium [registers that callback](https://github.com/edrlab/thorium-reader/blob/137e8901196bc47173580856105fe78b40473570/src/renderer/reader/components/Reader.tsx#L678) and [updates reading-position state](https://github.com/edrlab/thorium-reader/blob/137e8901196bc47173580856105fe78b40473570/src/renderer/reader/components/Reader.tsx#L3020-L3127).

The toolkit also exports [isLocatorVisible](https://github.com/edrlab/thorium-reader/blob/137e8901196bc47173580856105fe78b40473570/src/r2-xxx-js/r2-navigator-js/electron/renderer/location.ts#L1956-L2007): **an application-side query** of matching active webviews through correlated IPC. It is neither a publication API nor a committed surface-enter notification. A first-visible locator or geometric query alone would still need presentation, spread, transition and foreground semantics before it could safely activate PRIME.

## Reader location → speech → highlighting/navigation

Thorium's [EPUB read-aloud action](https://github.com/edrlab/thorium-reader/blob/137e8901196bc47173580856105fe78b40473570/src/renderer/reader/components/Reader.tsx#L3345-L3375) invokes the navigator `ttsPlay` traced below. Its separate voice-selection UI does not supply a publication location API.

[Application-side ttsPlay](https://github.com/edrlab/thorium-reader/blob/137e8901196bc47173580856105fe78b40473570/src/r2-xxx-js/r2-navigator-js/electron/renderer/readaloud.ts#L207-L257) consumes `getCurrentReadingLocation()`, selects the matching active document, and sends its selector/caret range in `R2_EVENT_TTS_DO_PLAY`. If unavailable, it falls back to the first webview. The [preload handler](https://github.com/edrlab/thorium-reader/blob/137e8901196bc47173580856105fe78b40473570/src/r2-xxx-js/r2-navigator-js/electron/renderer/webview/preload.ts#L5329-L5405) resolves the selector/range into DOM nodes. [Webview ttsPlay](https://github.com/edrlab/thorium-reader/blob/137e8901196bc47173580856105fe78b40473570/src/r2-xxx-js/r2-navigator-js/electron/renderer/webview/readaloud.ts#L134-L193) generates a text queue and chooses the corresponding item, or the first item if no match is found. Thus “start speaking here” uses a reader-maintained anchor; it does not establish that the whole document or PRIME surface has just arrived.

[Speech boundary and end handlers](https://github.com/edrlab/thorium-reader/blob/137e8901196bc47173580856105fe78b40473570/src/r2-xxx-js/r2-navigator-js/electron/renderer/webview/readaloud.ts#L1597-L1692) use `SpeechSynthesisUtterance`: word boundaries call `updateTTSInfo`, and utterance completion advances the queue (or pauses for manual-next). [Highlight/focus updates](https://github.com/edrlab/thorium-reader/blob/137e8901196bc47173580856105fe78b40473570/src/r2-xxx-js/r2-navigator-js/electron/renderer/webview/readaloud.ts#L983-L1195) use the supplied focus/scroll function; [focusScrollRaw](https://github.com/edrlab/thorium-reader/blob/137e8901196bc47173580856105fe78b40473570/src/r2-xxx-js/r2-navigator-js/electron/renderer/webview/preload.ts#L1998-L2027) scrolls into view, updates the anchor and notifies location. At document end/back, [the host TTS handler](https://github.com/edrlab/thorium-reader/blob/137e8901196bc47173580856105fe78b40473570/src/r2-xxx-js/r2-navigator-js/electron/renderer/readaloud.ts#L132-L201) invokes `navPreviousOrNext` across spine items. **Speech can drive navigation**, rather than merely report what silent reading presents.

The speech objects, queue and reader IPC run in reader preload/application code. Observing incidental injected highlights would depend on private implementation and require speech playback. Neither is a silent-reading contract.

## Media overlays

[Audio timeupdate](https://github.com/edrlab/thorium-reader/blob/137e8901196bc47173580856105fe78b40473570/src/r2-xxx-js/r2-navigator-js/electron/renderer/media-overlays.ts#L217-L250) compares the audio clock with the clip boundary and advances playback. [moHighlight](https://github.com/edrlab/thorium-reader/blob/137e8901196bc47173580856105fe78b40473570/src/r2-xxx-js/r2-navigator-js/electron/renderer/media-overlays.ts#L1390-L1470) maps the current text/audio pair to document href and fragment ID, obtains the publication's active/playback classes, and sends `R2_EVENT_MEDIA_OVERLAY_HIGHLIGHT` to the corresponding active webview. The [preload highlight handler](https://github.com/edrlab/thorium-reader/blob/137e8901196bc47173580856105fe78b40473570/src/r2-xxx-js/r2-navigator-js/electron/renderer/webview/preload.ts#L5500-L5770) applies presentation and, when necessary, scrolls the target into view, then reports the new reading location with overlay recursion suppressed. [mediaOverlaysNext](https://github.com/edrlab/thorium-reader/blob/137e8901196bc47173580856105fe78b40473570/src/r2-xxx-js/r2-navigator-js/electron/renderer/media-overlays.ts#L1755-L1829) can navigate to the target document/fragment or next spine item.

These are coordinated **playback** mechanisms. The existing silent-reading location notification can inform media overlays, but that does not dispatch a public arrival event back to EPUB scripts. No audio tracks, narration requirement or TTS workaround were added.

## What the publication can access

[Webview configuration](https://github.com/edrlab/thorium-reader/blob/137e8901196bc47173580856105fe78b40473570/src/r2-xxx-js/r2-navigator-js/electron/renderer/dom.ts#L310-L330) enables context isolation, disables Node integration and retains web security. The private preload's `ipcRenderer`, `READIUM2` state and `R2_EVENT_*` message handlers are not supported EPUB APIs. Reading their names in the source does not grant content access to them.

The [reading-system object](https://github.com/edrlab/thorium-reader/blob/137e8901196bc47173580856105fe78b40473570/src/r2-xxx-js/r2-navigator-js/electron/renderer/webview/epubReadingSystem.ts#L26-L60) and Thorium's [content-world injection](https://github.com/edrlab/thorium-reader/blob/137e8901196bc47173580856105fe78b40473570/src/main/streamer/streamerCommon.ts#L150-L187) expose name/version/feature detection; neither exposes current locator, arrival/departure subscriptions or the application-side toolkit functions. No private IPC, injected-internal hook, developer tools or security bypass is proposed for the EPUB.

| Quantity | Meaning | Why it cannot substitute for encounter |
| --- | --- | --- |
| Document load / pageshow | DOM instance exists / lifecycle event | Can precede presentation; prior native counterexample completes unseen |
| Document visibility / element intersection | Browser lifecycle or geometry | Does not identify the reader's committed displayed surface |
| Reader displayed location | Active href, page/column and anchor maintained by navigator | Available to the application; anchor alone is not component visibility |
| Speech position | Current queue item/word in an active speech session | Requires speech; can move the reader |
| PRIME actually presented | Component intersects the committed reading display, with departure/restore semantics | Required contract, not exposed by the inspected public interface |

## Standard and other implementations: scoped portability findings

- **EPUB standard:** inspected [EPUB Reading Systems 3.3, Recommendation 17 October 2024](https://www.w3.org/TR/2024/REC-epub-rs-33-20241017/), §6.4.2, Appendix B and §9. DOM/UI event support and `epubReadingSystem.hasFeature` do not define a committed-page enter/leave API. Media-overlay active classes and target visibility coordinate playback, not ordinary silent arrival. This is a finding about those specified mechanisms, not universal absence across every extension or future EPUB revision.
- **Documented reader-specific extension:** [Apple Books Asset Guide 5.3.1, embedded read-aloud controls](https://help.apple.com/itc/booksassetguide/en.lproj/itcd0c2f7c59.html) documents `ibooks:readaloud` start/stop and automatic/manual narration page turns. It controls read-aloud; it is not a documented silent-arrival subscription. Apple Books was not run; no iPad compatibility is claimed.
- **Other toolkit implementation:** [EPUB.js v0.3.93 Rendition source](https://github.com/futurepress/epub.js/blob/v0.3.93/src/rendition.js#L683-L750) reports location and emits `relocated` on the host's Rendition object. This is useful for a reader application, not an object promised inside every publication. No EPUB.js reader was built or natively tested.
- **Supported Readium application integration:** [Kotlin toolkit 3.1.2 migration guide](https://readium.org/kotlin-toolkit/3.1.2/migration-guide/) exposes observable `Navigator.currentLocator`; [registerJavascriptInterface](https://readium.org/kotlin-toolkit/3.1.2/api/readium/readium-navigator/org.readium.r2.navigator.epub/-epub-navigator-fragment/-configuration/register-javascript-interface.html) allows the embedding application to install a bridge per resource. These are documented app facilities, not an EPUB-standard bridge or functionality installed in Thorium. They show that an integration could use an existing toolkit. Locator updates would still need actual-presentation filtering and component geometry.

This limited survey finds real app APIs and a reader-specific narration extension. It does **not** infer universal lack of arrival APIs from Thorium, or claim compatibility tests for these other implementations.

## Smallest proposed reader-side contract — not implemented

Recommend discussing a supported presentation bridge with Thorium/Readium maintainers before another EPUB-only probe. No message was sent to maintainers in this task. The next experiment, if separately authorised, should be a tiny toolkit-host integration test, not a new publishing system or full reader.

An opt-in, versioned bridge could let EPUB scripts register a resource-local component ID/selector, obtain an initial snapshot and subscribe to ordered `enter`/`leave` changes. Payload: resource identity, component identity, document-instance ID, monotonic sequence, `presented` boolean and reason (turn, restore, foreground/background, layout). This is **a proposed extension**, not an existing event name or API. It must reveal no filesystem, Electron or arbitrary execution capability.

The reader must resolve resource + component geometry against the committed visible page/spread, suppress preloaded/offscreen instances, and deliver initial inactive state before exposing the scripted surface. Loading, DOM-ready and speech updates cannot substitute. An atomic snapshot/subscription handshake must cover late listeners and restore. Reader-side acknowledgement/presentation gating is needed to avoid revealing full text before scripting has installed its reserved blank surface. Two-page spreads, resize and interrupted transitions need explicit semantics. A location callback alone is insufficient.

A Readium host could combine its application locator/navigation APIs with a narrowly scoped content bridge; its own rendering layer must supply the final presentation decision. Thorium would require a supported reader change to relay that decision across its existing isolation boundary. No fork, patch or custom reader was built here.

Proposed content policy: first normal-motion enter starts a reserved blank surface; leave cancels timers and preserves progress; incomplete return resumes the saved prefix; completed return/reopening shows complete text with optional Replay. Immediate reveal marks complete. Reopening an incomplete performance resumes only after a fresh positive presentation snapshot. Reduced motion presents an understandable static state; no-script/unsupported readers retain readable text. These are proposed integration behaviours, not changes to the retained baseline or claims about probe reliability. Native turns must never await performance or lose keys to the bridge.

Acceptance for that future integration: timed native recordings with speech disabled, delayed arrival after preload, controlled invisible preload, first enter, departure during output, quick/later return, saved-position reopen, focused-control turns, reduced motion and no-script. Establish the supported contract first; then test all those cases. Existing recordings prove the old heuristic's limitation, not this unbuilt proposal.
